# HorseRPG v0.1 产品规格

> 状态：业务规则基线（v0.1）
> 范围：本文记录已经确认的业务规则，供后续数据库、权限和功能设计引用。本文不定义实现方案，也不替代 GM 的裁定。

## 1. 系统定位与裁定边界

HorseRPG 是 **Winning Post（WP）赛马跑团的辅助管理网站**。WP 负责实际赛马模拟；GM 是游戏事实与跑团规则的最终裁判。

网站负责承载玩家意图、GM 确认与修正，以及下列已确认业务的记录和确定性处理：马匹资料、幼驹交易、实时公开拍卖、比赛报名、赛果、统计、资金、奖金挂账、退役结算和操作历史。

网站可以提供规则检查、提示和辅助计算，但不得以自动化结果取代 GM 对 WP 实际情况或跑团规则的最终判断。关键流程的标准模式为：

```text
PLAYER 提出意图 → 网站检查可判定规则 → GM 确认或修正 → 网站记录结果 → 自动处理确定性统计/账务
```

GM 应能修正绝大多数业务数据；涉及已结算的关键事实时，修正必须可追溯。

## 2. 角色、账号和可见性

### 2.1 角色

系统只有两种权限角色：

| 角色 | 定义 |
| --- | --- |
| `PLAYER` | 代表一位 Owner 提交意图、查看公开资料，以及查看其 Owner 私有资料。 |
| `GM` | 最终裁判；可以查看与修改全部数据，并确认关键流程。 |

每个 `PLAYER` 账号必须绑定一个 Owner；Owner 可以暂时没有 `PLAYER` 账号。v0.1 中每个 Owner 最多绑定一个 `PLAYER` 账号。

### 2.2 信息公开与隔离

除下列两类数据外，玩家数据原则上不按 Owner 相互隔离。所有玩家均可查看公开的马匹、马主、比赛、公开拍卖信息和 Owner 资金汇总信息。以下数据必须按 Owner 隔离，只有所属 Owner 与 GM 可以查看：

| 私有数据 | 隔离范围 |
| --- | --- |
| 庭先取引秘密报价 | 报价 Owner 与 GM |
| 庭先取引私密 GM 评价 | 询问 Owner 与 GM |

公开拍卖中的当前价格、当前最高报价 Owner、最近报价和倒计时，对所有玩家公开。

公开资金汇总不得泄露或使人反推出当前庭先秘密报价或其冻结金额。逐笔财务流水是否公开仍待确认。

## 3. 时间体系

系统同时使用两套不可混用的时间。

| 时间 | 字段/类型 | 用途 |
| --- | --- | --- |
| WP 游戏时间 | `wp_year`、`wp_month`、`wp_week` | 出生、入厩、比赛、伤病、退役、游戏内赛程。 |
| 现实时间 | PostgreSQL `timestamptz` | `created_at`、`updated_at`、报价时间、拍卖倒计时、提交时间、GM 操作时间、审计日志。 |

公开拍卖的报价先后、竞价合法性和 10 秒截单必须以服务器现实时间为准。客户端只显示状态；Supabase Realtime 只用于多客户端广播，不能成为最终裁判。

## 4. 马匹

### 4.1 生命周期与伤病

马匹生命周期如下：

```text
FOAL → OWNED_FOAL → TRAINING → ACTIVE → RETIRE_PENDING → RETIRED → BREEDING
  └──────────────────────────────────────────────────────────────→ DISCARDED
```

`DISCARDED` 表示不再参与游戏；不得物理删除历史 Horse 数据。幼驹获得 Owner 后，预期路径为 `OWNED_FOAL → TRAINING → ACTIVE`。退役由 `ACTIVE → RETIRE_PENDING → GM 确认 → RETIRED → BREEDING` 逐步进行。

伤病不是生命周期。一匹 `ACTIVE` 马可以同时处于 `INJURED` 状态；伤病独立记录，伤病期间不能正常报名。伤病结束 WP 周按包含处理，自其结束周的下一 WP 周起才恢复正常报名资格。

### 4.2 基础公开资料

每匹 Horse 至少维护以下公开资料：

| 类别 | 字段 |
| --- | --- |
| 标识 | 系统内部 `id`、永久唯一 `horse_number` |
| 出生与命名 | `birth_year`、`foal_name`、可空 `name_katakana`、可空 `translated_name` |
| 属性与血统 | `sex`、`coat_color`、`sire_name`、`sire_line`、`broodmare_sire_name` |
| 当前归属 | Owner、当前主战骑手、当前调教师、`life_stage` |
| 记录时间 | `created_at`、`updated_at` |

主战骑手与调教师可以变更，v0.1 只保存当前值，不维护其变更历史。Horse 尚未取得 Owner 时可以没有 Owner；一旦取得，所有权不再转让。

### 4.3 血统因子

血统因子分为 `SIRE` 与 `MARE` 两类。每匹马每一类可以没有，最多两个。因子必须作为与 Horse 关联的独立记录管理；不得设计为 `factor_1`、`factor_2` 等固定列。

## 5. 资金、冻结和奖金

金额均使用 `bigint` 整数游戏资金单位，不得使用浮点数。正常 PLAYER 业务操作不得造成账户资金或可用资金为负。

| 概念 | 规则 |
| --- | --- |
| 账户资金 | `initial_funds` 加上已真正入账的 `financial_transactions`。 |
| 拍卖冻结资金 | Owner 当前全部庭先有效秘密报价，加上公开拍卖当前有效最高报价所占用的金额。冻结不产生真实扣款流水。 |
| 可用资金 | 账户资金减去拍卖冻结资金。有效报价的总冻结额不得超过可用账户资金。 |
| 待释放奖金 | 比赛取得并折算完成、但因马匹尚未退役而不能使用的奖金。 |
| 总资产 | 账户资金加待释放奖金；不计入马匹评价价值。 |

比赛奖金只会在相关 Horse 退役并完成结算后进入账户资金。资金纠错优先新增修正流水，不直接改写历史余额。

## 6. 0 岁幼驹与庭先取引

GM 在 WP 内完成配种；幼驹当年 4 月出生、同年 8 月进入庭先取引。一匹幼驹只参加其出生批次的一届庭先取引。

庭先期间，所有玩家仅公开看到幼驹外观、血统和最低报价。任何玩家不得看到是否有人报价、报价人数、当前最高价、自己是否领先、其他 Owner 的报价金额、其他 Owner 询问的幼驹或其 GM 评价。

### 6.1 询问 GM 评价

每届庭先取引中，一个 Owner 只能选择一匹幼驹询问 GM 评价。GM 的回答仅该 Owner 可见。该“一届一次”的规则必须由数据层保证，而非仅依赖界面限制。

### 6.2 秘密报价

Owner 可以对多匹幼驹秘密报价；对同一幼驹只有一笔当前有效报价。截止前可创建、修改或撤回报价，且每笔当前有效报价均全额冻结资金。系统不得允许任意 Owner 的全部有效报价冻结额超过其可用账户资金。

截止后报价锁定。每匹马由最高当前有效报价获胜；若金额相同，则以当前有效报价较早形成者获胜。报价修改到其他金额后再改回原金额，其同价优先时间按新的当前报价形成时间计算。

截止后交易先进入等待 GM 核对状态；最终 Horse 所有权与扣款必须由 GM 确认后才生效。

## 7. 年末公开拍卖

庭先取引后仍无主的幼驹，按 `LOT 001 → LOT 002 → LOT 003 …` 逐匹进入同年年末公开拍卖。同一时刻只可拍卖一匹。公开拍卖流拍后，Horse 设置为 `DISCARDED`；不得重新进入后续庭先或公开拍卖。

每个 Lot 展示：幼驹名、五个评分槽与各自评语、性别、毛色、起拍价、评价价值、母父、牝马因子、父、父系统、种父因子和拍卖编号。五个评分槽固定为 slot 1–5，每个 slot 包含 1 至 5 星与一段评语，模拟五个评价来源，并不代表真实存在五名 GM。评价价值与起拍价是不同字段。

### 7.1 实时竞价与成交

1. GM 展示当前 Lot 后点击开始竞价。
2. 玩家进行公开竞价；所有玩家实时看到当前价格、当前最高报价 Owner、最近报价和倒计时。
3. 每次服务器接受一笔合法新报价，均设置 `close_at = 服务器当前时间 + 10 秒`。
4. 连续 10 秒没有合法新报价后，Lot 停止接受报价并进入等待 GM 确认。
5. GM 确认成交后，扣除成交 Owner 资金、为 Horse 分配 Owner，并写入财务流水；无人报价时 GM 确认流拍。

数据库服务器负责报价合法性和截单判定；Realtime 仅广播状态。当前最高报价应冻结相应资金，且冻结不是真实资金流水。年末拍卖后仍无主的 Horse 设置为 `DISCARDED`，保留完整历史记录。

## 8. 有主幼驹、入厩与参赛

### 8.1 有主幼驹

Owner 在马匹 1 岁至 2 岁的年末指定正式片假名马名、中文译名、调教师与主战骑手；随后在 2 岁进入入厩阶段，并按生命周期变为 `TRAINING`、`ACTIVE`。

### 8.2 比赛库

比赛分为未胜利战、条件赛、OP、G3、G2、G1。OP 及以上维护固定比赛库，至少保存比赛名、WP 月、WP 周、级别和其他必要资料。未胜利战与条件赛不维护完整固定库：报名时只选类别与 WP 年月周，具体比赛由 GM 与玩家依据 WP 实际情况确定。

### 8.3 报名

出道战由 WP 游戏内调教师决定，由 GM 记录。出道战完成后，玩家可主动提交未来多场报名，每笔可指定：WP 年、月、周，比赛或比赛类别，希望使用的主战骑手、跑法和备注。

同一 Horse 同一 WP 周只能参加一场比赛。玩家可撤回尚未执行的报名。GM 可确认、修改后确认、拒绝、撤回或主动代玩家创建报名。伤病中的 Horse 不得正常报名；主战骑手不可用时，实际骑手由玩家与 GM 协调。

当多匹玩家马参加同一实际比赛时，系统应提示或限制游戏规则规定的特殊跑法；GM 可据此拒绝报名。网站只处理可判定的明显错误，GM 始终拥有最终修改与裁定权。

## 9. 比赛、体力、伤病和统计

GM 在 WP 内实际操作比赛，网站不与 WP 自动同步。`race_entries` 记录报名意图，`actual_races` 记录 GM 最终在 WP 中执行的一场实际比赛；一场 `actual_race` 可以关联多匹玩家 Horse 的 `race_results`。赛后由 GM 回填实际比赛、名次、WP 赏金、实际骑手、实际跑法和必要备注。

系统根据确认后的赛果自动统计 Horse 的出赛次数、胜场、亚军、季军、G1 胜场、总 WP 赏金和主要胜鞍。这些统计是赛果的派生结果，原则上不得作为 Horse 的手工维护字段。

体力结算在 v0.1 完全由 GM 根据 WP 未同步的动态数据自行计算、投骰并填写最终结果；`condition_records` 只记录 GM 的最终裁定。网站不从该记录自动推导“正确”的体力或伤病结论；未来辅助计算器只能给出建议。

伤病由 GM 确认是否伤病、WP 开始时间、WP 结束时间和备注；伤病期间 Horse 无法正常报名。

## 10. 奖金与退役

GM 回填比赛 WP 赏金后，由 GM 输入或确认最终的 Prize Receivable 金额。网站未来可提供折算辅助，但 `prize_receivables.amount` 不要求由数据库按固定公式自动计算。确认后生成状态为 `PENDING` 的 Prize Receivable，计入 Owner 待释放奖金而不进入可用资金。

Horse 退役后，属于该 Horse 的全部 `PENDING` Prize Receivable 一次性释放：生成正式 Financial Transaction，并将状态变更为 `RELEASED`。该流程必须防止重复退役结算导致奖金重复到账。赛果在已产生奖金应收或奖金已释放后被修正时，必须通过受控调整处理，不能再次生成或释放重复奖金。

主动退役在 Horse 满 3 岁后由 Owner 向 GM 提出，GM 最终确认。强制退役包括 WP 游戏内寿命过低时由 GM 年末执行，或 G1 胜利达到 9 次。网站可提示条件已满足，但不得自动替 GM 退役。退役后 Horse 操作权归 GM；繁殖系统不属于 v0.1 主要开发范围。

## 11. 审计、修正与操作权限

GM 对以下关键变更必须留下 Audit Log：资金、比赛结果、WP 赏金、拍卖结果、庭先成交、伤病、退役、奖金释放，以及其他已经结算的重要数据。已结算核心数据允许 GM 纠错，但必须审计；财务纠错使用追加修正流水。

审计记录应明确操作人、发生现实时间、操作对象、动作、变更前后内容或可追溯引用及原因/备注（如有）。玩家所提交的意图与 GM 的确认、拒绝、修改、撤回也应保留操作历史。审计用于追溯，不赋予系统推翻 GM 最终裁定的权力。

## 12. v0.1 明确不做的事情

本阶段只整理业务规格。不得创建数据库 migration、修改 Supabase 远程数据库、创建 production table、开发 UI/Auth/拍卖/比赛功能、安装 ORM 或改变既有项目架构。

## Open Questions

以下事项在当前规则中仍缺少足以直接实现校验、RLS 或用户行为的定义，需产品方确认：

1. 秘密报价最低报价、公开拍卖起拍价与最小加价单位的精确规则；公开拍卖能否撤回、最高价 Owner 能否再次出价，以及 GM 是否能改价或重开已关闭 Lot。
2. 公开资金汇总的确切展示字段（不得反推秘密报价/冻结），以及逐笔 `financial_transactions` 是否公开。
3. `initial_funds` 的设定与变更方式，以及 GM 已审计纠错是否允许使账户资金为负。
4. 固定比赛库的完整资料、`actual_races` 的标准实际比赛标识，以及未胜利战/条件赛报名在 GM 回填前后能否变更 WP 周或类别。
5. “主要胜鞍”、特殊跑法、满 3 岁、寿命过低与 G1 九胜的精确判定和后续系统动作。
6. 生命周期允许的完整跳转，特别是 `RETIRED → BREEDING` 是否必经，以及除公开拍卖流拍外哪些情况可以进入 `DISCARDED`。
