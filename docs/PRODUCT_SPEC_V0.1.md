# HorseRPG v0.1 产品规格

> 状态：业务规则基线（v0.1）
> 范围：本文记录已经确认的业务规则，供后续数据库、权限和功能设计引用。本文不定义实现方案，也不替代 GM 的裁定。

## 1. 系统定位与裁定边界

HorseRPG 是 **Winning Post（WP）赛马跑团的辅助管理网站**。WP 负责实际赛马模拟；GM 是游戏事实与跑团规则的最终裁判。

网站负责承载玩家意图、GM 确认与修正，以及下列已确认业务的记录和确定性处理：马匹资料、幼驹交易、实时公开拍卖、比赛报名、赛果、统计、资金、奖金挂账、退役结算和操作历史。

网站可以提供规则检查、提示和辅助计算，但不得以自动化结果取代 GM 对 WP 实际情况或跑团规则的最终判断。关键流程的标准模式为：

```text
PLAYER 提出意图 → 网站检查可判定规则 → GM 确认或修正 → 网站记录结果 → 自动处理确定性统计/账务
```

GM 应能修正绝大多数业务数据；涉及已结算的关键事实时，修正必须可追溯。

## 2. 角色、账号和可见性

### 2.1 角色

系统只有两种权限角色：

| 角色 | 定义 |
| --- | --- |
| `PLAYER` | 代表一位 Owner 提交意图、查看公开资料，以及查看其 Owner 私有资料。 |
| `GM` | 最终裁判；可以查看与修改全部数据，并确认关键流程。 |

每个 `PLAYER` 账号必须绑定一个 Owner；Owner 可以暂时没有 `PLAYER` 账号。v0.1 中每个 Owner 最多绑定一个 `PLAYER` 账号。

### 2.2 信息公开与隔离

除下列两类数据外，玩家数据原则上不按 Owner 相互隔离。所有玩家均可查看公开的马匹、马主、比赛、公开拍卖信息和 Owner 资金汇总信息。以下数据必须按 Owner 隔离，只有所属 Owner 与 GM 可以查看：

| 私有数据 | 隔离范围 |
| --- | --- |
| 庭先取引秘密报价 | 报价 Owner 与 GM |
| 庭先取引私密 GM 评价 | 询问 Owner 与 GM |

公开拍卖中的当前价格、当前最高报价 Owner、最近报价和倒计时，对所有玩家公开。

庭先报价阶段完全秘密：在 GM 确认最终结算前，任何 PLAYER 都不得得知其他 Owner 是否报价、报价数、报价金额、领先情况、询问对象或私密 GM 评价。GM 确认 Settlement 后，最终成交 Owner 与最终成交价格对所有已认证 PLAYER 公开；所有失败报价及全部报价历史仍永久私密。

公开资金汇总不得泄露或使人反推出当前庭先秘密报价或其冻结金额。逐笔财务流水是否公开仍待确认。

## 3. 时间体系

系统同时使用两套不可混用的时间。

| 时间 | 字段/类型 | 用途 |
| --- | --- | --- |
| WP 游戏时间 | `wp_year`、`wp_month`、`wp_week` | 出生、入厩、比赛、伤病、退役、游戏内赛程。 |
| 现实时间 | PostgreSQL `timestamptz` | `created_at`、`updated_at`、报价时间、拍卖倒计时、提交时间、GM 操作时间、审计日志。 |

公开拍卖的报价先后、竞价合法性和 10 秒截单必须以服务器现实时间为准。客户端只显示状态；Supabase Realtime 只用于多客户端广播，不能成为最终裁判。

## 4. 马匹

### 4.1 生命周期与伤病

马匹生命周期如下：

```text
FOAL → OWNED_FOAL → TRAINING → ACTIVE → RETIRE_PENDING → RETIRED → BREEDING
  └──────────────────────────────────────────────────────────────→ DISCARDED
```

`DISCARDED` 表示不再参与游戏；不得物理删除历史 Horse 数据。幼驹获得 Owner 后，预期路径为 `OWNED_FOAL → TRAINING → ACTIVE`。退役由 `ACTIVE → RETIRE_PENDING → GM 确认 → RETIRED → BREEDING` 逐步进行。

伤病不是生命周期。一匹 `ACTIVE` 马可以同时处于 `INJURED` 状态；伤病独立记录，伤病期间不能正常报名。伤病结束 WP 周按包含处理，自其结束周的下一 WP 周起才恢复正常报名资格。

### 4.2 基础公开资料

每匹 Horse 至少维护以下公开资料：

| 类别 | 字段 |
| --- | --- |
| 标识 | 系统内部 `id`、永久唯一 `horse_number` |
| 出生与命名 | `birth_year`、`foal_name`、可空 `name_katakana`、可空 `translated_name` |
| 属性与血统 | `sex`、`coat_color`、`sire_name`、`sire_line`、`broodmare_sire_name` |
| 当前归属 | Owner、当前主战骑手、当前调教师、`life_stage` |
| 记录时间 | `created_at`、`updated_at` |

主战骑手与调教师可以变更，v0.1 只保存当前值，不维护其变更历史。Horse 尚未取得 Owner 时可以没有 Owner；一旦取得，所有权不再转让。

### 4.3 血统因子

血统因子分为 `SIRE` 与 `MARE` 两类。每匹马每一类可以没有，最多两个。因子必须作为与 Horse 关联的独立记录管理；不得设计为 `factor_1`、`factor_2` 等固定列。

## 5. 资金、冻结和奖金

金额均使用 `bigint` 整数游戏资金单位，不得使用浮点数。正常 PLAYER 业务操作不得造成账户资金或可用资金为负。

| 概念 | 规则 |
| --- | --- |
| 账户资金 | `initial_funds` 加上已真正入账的 `financial_transactions`。 |
| 拍卖冻结资金 | Owner 当前全部庭先有效秘密报价，加上公开拍卖当前 Round 最高报价所占用的金额。公开 Round 在 `BIDDING` 或已关闭但尚未最终结算时继续冻结；被超价、作废为历史 Round 或已结算的报价不冻结。冻结不产生真实扣款流水。 |
| 可用资金 | 账户资金减去拍卖冻结资金。有效报价的总冻结额不得超过可用账户资金。 |
| 待释放奖金 | 比赛取得并折算完成、但因马匹尚未退役而不能使用的奖金。 |
| 总资产 | 账户资金加待释放奖金；不计入马匹评价价值。 |

比赛奖金只会在相关 Horse 退役并完成结算后进入账户资金。资金纠错优先新增修正流水，不直接改写历史余额。

## 6. 0 岁幼驹与庭先取引

GM 在 WP 内完成配种；幼驹当年 4 月出生、同年 8 月进入庭先取引。一匹幼驹只参加其出生批次的一届庭先取引。

### 6.0 草稿配置与现实时间

GM 创建庭先届次时，现实时间按**中国标准时间**选择开始日期、预设开始时刻（09:00、12:00、18:00、20:00、21:00 或 22:00）和报价时长（1、3、6、12 小时，或 1、3、7 天）；系统换算并保存权威 `timestamptz` 开始/截止时间，所有报价与结算仍以数据库服务器时间裁定。

在届次仍为 `DRAFT`、数据库服务器尚未到达开始时间、且没有询问、秘密报价、报价历史或结算事实时，GM 可填写原因后移除整个草稿届次，或移除其中单个草稿 Lot。移除的是从未正式参与业务的配置行，对应 Horse 可以重新配置；Session/Lot 的移除原因和移除前资料必须保留在 Audit Log。任何已开始、已有玩家意图、报价或结算的庭先数据不得物理删除。

庭先报价阶段，所有玩家仅公开看到幼驹外观、血统和最低报价。任何玩家不得看到是否有人报价、报价人数、当前最高价、自己是否领先、其他 Owner 的报价金额、其他 Owner 询问的幼驹或其 GM 评价。

### 6.1 询问 GM 评价

每届庭先取引中，一个 Owner 只能选择一匹幼驹询问 GM 评价。GM 的回答仅该 Owner 可见。该“一届一次”的规则必须由数据层保证，而非仅依赖界面限制。

### 6.2 秘密报价

Owner 可以对多匹幼驹秘密报价；对同一幼驹只有一笔当前有效报价。最低报价 `minimum_price` 可以为 0，报价必须不低于该 Lot 的最低报价。截止前可创建、修改或撤回报价，且每笔当前有效报价均全额冻结资金。系统不得允许任意 Owner 的全部有效报价冻结额超过其可用账户资金。

截止后报价锁定。GM 的正常结算必须确认系统推荐赢家：按 `amount DESC, priority_at ASC, id ASC` 选择。报价修改到其他金额后再改回原金额，其同价优先时间按新的当前报价形成时间计算。

GM 可走独立的异常裁定路径，选择另一条仍有效的报价，但必须填写非空 `override_reason`，同时保留系统推荐报价与最终选择报价，并写入 Audit Log。该路径仍须满足截止、资金、Owner、Lot 与幂等结算约束；PLAYER 绝不能调用。最终 Horse 所有权与扣款必须由 GM 确认后才生效。确认后公开最终成交 Owner 与最终成交价格；失败报价和完整报价历史仍不公开。

## 7. 年末公开拍卖

庭先取引后仍无主的幼驹，按 `LOT 001 → LOT 002 → LOT 003 …` 逐匹进入同年年末公开拍卖。同一 Event 同一时刻只可拍卖一匹。公开拍卖资格仅限：无 Owner、`FOAL`、出生年等于该 Event WP 年、且已经参加同年庭先并最终未成交的 Horse。每匹 Horse 全局至多进入一个公开拍卖 Lot。正常流拍后 Horse 设置为 `DISCARDED`，不得重新进入后续庭先或公开拍卖；Emergency Rollback 创建的是同一 Lot 的新 Round，不是新 Lot。

每个 Lot 展示：幼驹名、五个评分槽与各自评语、性别、毛色、起拍价、评价价值、母父、牝马因子、父、父系统、种父因子和拍卖编号。五个评分槽固定为 slot 1–5，每个 slot 包含 1 至 5 星与一段评语，模拟五个评价来源，并不代表真实存在五名 GM。评价价值与起拍价是不同字段。

### 7.1 实时竞价与成交

1. GM 先展示当前 Lot 的 Horse 资料与五份评分；展示只公开该 Lot，不启动任何期限或改变 Round。随后 GM 单独点击开始，Lot 才进入 `OPEN_WAITING`；此时不存在 10 秒倒计时，服务器设置 10 分钟无报价兜底时间。
2. 所有报价必须是 `100000`（10 万）整数倍。第一口允许等于起拍价，且必须不低于起拍价；后续报价必须至少比当前价高一个 Event 的最低加价单位（当前固定为 10 万），允许跳价。
3. 当前最高报价 Owner 不能再次报价；已接受 Bid 不可撤回、不可修改、不可删除。客户端每次报价必须携带其看到的当前 `round_id` 与请求幂等键；Round 已切换时服务器拒绝该过期请求。同一 Owner、同一 Round、同一幂等键只可重试同一金额，重试返回原 Bid 且不改变任何竞价事实；同键不同金额必须拒绝。
4. 第一笔合法报价才使 Lot 进入 `BIDDING`，并以该笔最终被数据库接受的服务器 `accepted_at` 精确设置 `close_at = accepted_at + 10 秒`。每笔后续合法报价同样以其自身最终 `accepted_at` 重新设置 10 秒。
5. 服务器时间到达 `close_at` 后不再接受报价；`OPEN_WAITING` 到达 10 分钟无报价兜底后也不再接受第一口。两种情况都只进入 `CLOSED` 等待 GM，绝不自动成交、流拍或丢弃 Horse。
6. GM 在 `CLOSED` 后确认成交时，扣除赢家资金、为 Horse 分配 Owner、写入追加式财务流水与审计；无人报价时 GM 确认流拍。成交/流拍均幂等，不能重复扣款或重复改变 Horse。

Event 状态机为：`DRAFT → OPEN → CLOSED`，`CLOSED → OPEN` 或在所有 Lot 都已 `SOLD`/`PASSED` 且不存在待确认 Emergency Rollback 时 `CLOSED → SETTLED`；同状态请求是无副作用重试。`OPEN → CLOSED` 前不得存在 `OPEN_WAITING` 或 `BIDDING` 的活跃 Lot。`SETTLED` 不允许普通状态变更。

在 Event 为 `DRAFT` 时，GM 可填写原因后移除 Event，或移除其中 `QUEUED`、从未 Reveal、从未开始、没有 Bid、Settlement 或 Rollback 历史的 Lot。移除 Event 时可一并移除其全部满足这些条件的草稿 Lot、初始 Round 与草稿评价；每个被移除对象均须审计。Event 一旦 `OPEN`，或 Lot 已 Reveal/开始/产生任何业务历史，即不得走物理移除路径。

数据库服务器负责报价合法性、资金冻结和截单判定；Realtime 仅广播状态。当前 Round 最高报价应冻结相应资金，且冻结不是真实资金流水。所有已认证 PLAYER 可读取 Event，以及 GM 已展示 Lot 的资料/评分、该 Lot 当前 Round 的已接受 Bid、当前价、当前赢家、倒计时与最终结果；未展示的未来 Lot、评分、Round 与 Bid 均不可读取。匿名访问者不可读取业务数据。Emergency Rollback 后的旧 Round 与 Bid 保留为 GM/audit 历史，不作为普通公开竞价显示。

### 7.2 CLOSED 普通重开

尚未最终 `SOLD` 或 `PASSED` 的 `CLOSED` Lot，GM 可填写非空原因后普通重开。已有报价时恢复为 `BIDDING`，保留 Bid、当前价和赢家，并从服务器当前时间重新给 10 秒；无报价时恢复为 `OPEN_WAITING`，并重新给 10 分钟无报价期限。普通重开不得删除 Bid，也不得改变起拍价。`SOLD` 与 `PASSED` 绝不能走普通重开。

### 7.3 Emergency Rollback

Emergency Rollback 仅用于已经最终 `SOLD` 或 `PASSED` 的重大异常，不是普通重开。GM 必须先以非空原因创建申请；申请本身不得改动 Horse、资金、Bid 或 Settlement。随后 GM 必须输入数据库保存的严格确认文本（例如 `ROLLBACK LOT 027`）才能执行。

执行 `SOLD` Rollback 时，原 Bid、Settlement 与购买扣款全部保留；系统新增同额 `PUBLIC_AUCTION_ROLLBACK` 补偿流水，将 Horse 从该 Settlement Owner 受控回退为无 Owner 的 `FOAL`，将原 Round 标为 `VOIDED`，并创建从起拍价重新开始的新 Round。执行 `PASSED` Rollback 时，Horse 从 `DISCARDED` 受控恢复为无 Owner 的 `FOAL`，同样作废旧 Round 并创建新 Round，但不产生资金补偿。若 Event 当时为 `CLOSED` 或 `SETTLED`，确认 Rollback 必须受控将其恢复为 `OPEN`、写入专门 Audit，随后新 Round 才可重新开拍。每个 Settlement 至多成功 Rollback 一次；重复确认不得二次退款、重复新建 Round 或篡改历史。申请、确认、补偿和新 Round 必须完整 Audit，且 rollback 原因不对 PLAYER 公开。

## 8. 有主幼驹、入厩与参赛

### 8.1 有主幼驹

Owner 在马匹 1 岁至 2 岁的年末指定正式片假名马名、中文译名、调教师与主战骑手；随后在 2 岁进入入厩阶段，并按生命周期变为 `TRAINING`、`ACTIVE`。

### 8.2 比赛库

比赛分为未胜利战、条件赛、OP、G3、G2、G1。`race_catalog` 维护 OP、G3、G2、G1 的可选固定比赛，至少保存名称、级别、默认 WP 月/周与启用状态；默认月/周只是填写时的参考，绝不是最终已确认赛程的硬约束。未胜利战、条件赛和其他非固定赛程使用 `MAIDEN`、`CONDITION` 或 `OTHER` 类别加非空比赛名称，不建立完整固定目录。比赛目录由 GM 维护，所有 authenticated 用户可读。

### 8.3 报名

出道战由 WP 游戏内调教师决定，由 GM 记录。出道战完成后，玩家可主动提交未来多场报名，每笔以 `race_entry_requests` 保存**原始意图**：自己的 ACTIVE Horse、请求 WP 年/月/周、固定比赛或类别型比赛、可空希望骑手、可空跑法与备注。当前 WP 周允许报名；早于 `game_state` 当前周的申请被数据库拒绝。

GM 审核 PENDING 意向后可拒绝，或创建单独的 `confirmed_race_entries` 权威赛程。GM 的最终 WP 年/月/周与比赛可以不同于 PLAYER 请求，且两套资料都永久保留；确认最少只需 Horse、最终 WP 时间与明确比赛身份，骑手、跑法和 GM 备注均可为空。对于没有 PLAYER 意向、但已有 Owner 且处于 ACTIVE 的 Horse，GM 也可以使用受控的 Direct Confirm 路径直接创建权威赛程；Owner 必须由 Horse 自动派生，不能由客户端指定。PLAYER 只能撤回自己的 PENDING 意向，不能自行确认、修改最终赛程或撤回已确认赛程。

同一 Horse 同一**最终确认** WP 周最多一条 `confirmed_race_entries`；多个同周 PENDING 意向合法。确认时数据库重新检查 Horse 仍为 ACTIVE、拥有合法 Owner、最终周不早于当前游戏周，并以伤病结束周包含的规则检查 ACTIVE injury；Request Confirm 还必须确认 Horse 仍属于请求 Owner。主战骑手不可用时，最终安排骑手可由 GM 留空或调整；实际骑手与实际跑法属于未来赛果，不覆盖赛前确认记录。所有 authenticated 用户只能读取安全公开赛程投影，其中不含 Request 来源、GM 备注或确认 GM；请求及其审核资料继续仅对所属 PLAYER 与 GM 可见。

当多匹玩家马参加同一实际比赛时，系统应提示或限制游戏规则规定的特殊跑法；GM 可据此拒绝报名。网站只处理可判定的明显错误，GM 始终拥有最终修改与裁定权。

## 9. 比赛、体力、伤病和统计

GM 在 WP 内实际操作比赛，网站不与 WP 自动同步。`confirmed_race_entries` 是赛前权威安排，`actual_races` 是 GM 在 WP 中实际执行的一场比赛，`race_results` 是某匹 Horse 的赛后事实；三者物理分离，实际比赛的时间、比赛、骑手和跑法可以不同于赛前安排，且不得以赛果覆盖计划事实。一场 `actual_races` 可以关联多匹 Horse 的多个 `race_results`，以表达多人同场。实际比赛只能记录在当前或过去的 WP 周，不能记录未来周。

固定比赛的实际赛果创建时必须从 `race_catalog` 复制比赛名称与 Grade 到 `actual_races` 作为历史快照；之后目录改名或停用不得改变过去比赛。非固定比赛使用 GM 填写的非空比赛名，不关联 Catalog，且 Grade 为 NULL。赛果由 GM 受控录入、修正或作废：同一确认赛程同一时间只有一个有效赛果；重复录入完全相同事实返回原赛果，不同事实必须走更正流程；作废保留历史并允许重新录入。基础表和 GM 备注不对 PLAYER 公开，PLAYER 仅通过不含操作者、GM Note 与作废历史的安全公开投影读取当前有效赛果。

`race_results.prize_amount` 是 GM 从 WP 输入的最终**赛果事实**，金额使用 `bigint`，可为 0，当前不生成 `financial_transactions`、不改变 Owner 资金、也不创建 Prize Receivable。v0.4-D 奖金模块部署后，必须扩展赛果更正与作废流程，对已生成的应收采用受控调整，避免重复入账。

系统可从当前有效赛果动态统计 Horse 的出赛次数、胜场、亚军、季军、G1 胜场、总 WP 赏金和主要胜鞍；这些统计不得作为 Horse 的手工维护字段。

体力结算在 v0.1 完全由 GM 根据 WP 未同步的动态数据自行计算、投骰并填写最终结果；`condition_records` 只记录 GM 的最终裁定。网站不从该记录自动推导“正确”的体力或伤病结论；未来辅助计算器只能给出建议。

伤病由 GM 确认是否伤病、WP 开始时间、WP 结束时间和备注；伤病期间 Horse 无法正常报名。

## 10. 奖金与退役

v0.4-D 将在 GM 依据赛果输入或确认最终 Prize Receivable 金额后，创建状态为 `PENDING` 的 Prize Receivable，计入 Owner 待释放奖金而不进入可用资金。网站未来可提供折算辅助，但 `prize_receivables.amount` 不要求由数据库按固定公式自动计算；它不等同于当前已记录但尚未入账的 `race_results.prize_amount`。

Horse 退役后，属于该 Horse 的全部 `PENDING` Prize Receivable 一次性释放：生成正式 Financial Transaction，并将状态变更为 `RELEASED`。该流程必须防止重复退役结算导致奖金重复到账。赛果在已产生奖金应收或奖金已释放后被修正时，必须通过受控调整处理，不能再次生成或释放重复奖金。

主动退役在 Horse 满 3 岁后由 Owner 向 GM 提出，GM 最终确认。强制退役包括 WP 游戏内寿命过低时由 GM 年末执行，或 G1 胜利达到 9 次。网站可提示条件已满足，但不得自动替 GM 退役。退役后 Horse 操作权归 GM；繁殖系统不属于 v0.1 主要开发范围。

## 11. 审计、修正与操作权限

GM 对以下关键变更必须留下 Audit Log：资金、比赛结果、WP 赏金、拍卖结果、庭先成交、伤病、退役、奖金释放，以及其他已经结算的重要数据。已结算核心数据允许 GM 纠错，但必须审计；财务纠错使用追加修正流水。

审计记录应明确操作人、发生现实时间、操作对象、动作、变更前后内容或可追溯引用及原因/备注（如有）。玩家所提交的意图与 GM 的确认、拒绝、修改、撤回也应保留操作历史。审计用于追溯，不赋予系统推翻 GM 最终裁定的权力。

## 12. v0.1 明确不做的事情

本阶段只整理业务规格。不得创建数据库 migration、修改 Supabase 远程数据库、创建 production table、开发 UI/Auth/拍卖/比赛功能、安装 ORM 或改变既有项目架构。

## Open Questions

以下事项在当前规则中仍缺少足以直接实现校验、RLS 或用户行为的定义，需产品方确认：

1. 公开资金汇总的确切对外展示字段（不得反推秘密报价/冻结），以及逐笔 `financial_transactions` 是否公开。
2. `initial_funds` 的设定与变更流程，以及经 GM 审计的纠错是否允许使账户资金为负；常规 PLAYER 操作已确定不得导致负数。
3. “主要胜鞍”、特殊跑法、满 3 岁、寿命过低与 G1 九胜触发后的精确判定和系统动作。
4. 生命周期允许的完整跳转，特别是 `RETIRED → BREEDING` 是否必经，以及除公开拍卖流拍外哪些情况可以进入 `DISCARDED`。
